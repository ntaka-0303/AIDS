# DocGen Skill - テンプレートマッピング定義

各テンプレートのセクションと、対応するproject_stateデータソースのマッピング。

## 成果物の依存関係

成果物は以下の階層構造を持つ。下位成果物は上位成果物もインプットとして参照する。

| 成果物 | 階層 | 上位成果物（インプット） |
|--------|------|------------------------|
| proposal_draft.md | 最上位 | なし |
| project_plan_draft.md | 2階層目 | proposal_draft.md |
| requirements_draft.md | 3階層目 | proposal_draft.md, project_plan_draft.md |

※ 週次報告書（weekly_report_draft.md）は WeeklyReport Skill で生成

---

## 1. proposal_draft.md（提案書）

**テンプレート**: `templates/proposal.md`
**出力先**: `outputs/proposal_draft.md`
**上位成果物**: なし（最上位）

### セクション別マッピング

| セクション | データソース | 抽出内容 |
|-----------|------------|---------|
| 1. 表紙 | project_charter.md | 顧客名、プロジェクト名、提出日 |
| 2. アジェンダ | - | テンプレート固定 |
| 3. 本提案の概要（エグゼクティブサマリー） | project_charter.md, requirements_master.md | 目的、主要課題、提案概要 |
| 4. 課題認識 | requirements_master.md | 現状課題、業務上の課題 |
| 5. 解決アプローチ | decisions.yaml, requirements_master.md | 解決方針、採用技術 |
| 6. AIWorkforce（AIエージェントプラットフォーム）の概要 | - | テンプレート固定（製品説明） |
| 7. 提供価値（ROI・工数削減） | project_charter.md | 期待効果、削減工数 |
| 8. 主要ユースケース | requirements_master.md | 機能要件から主要ユースケースを抽出 |
| 9. 導入ステップとスケジュール | project_charter.md, wbs.yaml | スケジュール概要、フェーズ構成 |
| 10. プロジェクト体制 | project_charter.md | 体制図、役割分担 |
| 11. リスクと対策 | risks.yaml | 主要リスクと対策 |

### データ抽出ルール

**requirements_master.md から:**
```
課題認識 → 「現状課題」「背景」セクションから抽出
ユースケース → 機能要件（REQ-XXX type=functional）から抽出
```

**risks.yaml から:**
```
impact=高 または probability=高 のリスクを優先表示
status=Open のもののみ表示
最大5件まで
```

### 品質チェックポイント（訴求力・説得力重視）

提案書は「受注獲得」が目的。正確性より訴求力を優先する。

| チェック項目 | 確認内容 | NG例 |
|-------------|---------|------|
| **顧客視点** | 「貴社」の課題・メリットが主語になっているか | 「弊社のソリューションは...」が多すぎる |
| **ストーリー** | 課題→解決策→価値の流れが論理的か | いきなり機能説明から始まる |
| **定量化** | ROI、削減率、効果が数値で示されているか | 「大幅に改善」「効率化」のみ |
| **差別化** | 競合との違い、自社の強みが明確か | 一般的な説明のみ |
| **サマリー** | エグゼクティブサマリーで3分で概要が伝わるか | 長文で要点が不明 |
| **専門用語** | 顧客が理解できる言葉で書かれているか | 技術用語の羅列 |

**生成時の文体指針:**
- 能動態を使用（「〜されます」→「〜します」）
- 具体的な数値を含める（「約30%の工数削減」）
- ベネフィットを先に記述（機能説明より効果を先に）
- 短い文で簡潔に（1文50文字以内目安）

## 2. project_plan_draft.md（プロジェクト計画書）

**テンプレート**: `templates/project_plan.md`
**出力先**: `outputs/project_plan_draft.md`
**上位成果物**: `outputs/proposal_draft.md`

### セクション別マッピング

| セクション | データソース | 抽出内容 |
|-----------|------------|---------|
| 1. 表紙 | project_charter.md | プロジェクト名、作成日、バージョン |
| 2. 本計画書の目的・位置づけ | project_charter.md, **proposal_draft.md** | 目的、適用範囲、背景（提案書と整合） |
| 3. プロジェクトのゴール・KGI/KPI | project_charter.md, **proposal_draft.md** | 目的、成功基準、KPI（提案書と整合） |
| 4. 対象範囲・スコープ定義 | project_charter.md, decisions.yaml, **proposal_draft.md** | スコープ内/外、スコープ変更決定（提案書の内容を詳細化） |
| 5. プロジェクト体制 | project_charter.md, **proposal_draft.md** | 体制図、連絡先、RACI（提案書の体制を詳細化） |
| 6. フェーズ構成とスケジュール | wbs.yaml, **proposal_draft.md** | フェーズ一覧、マスタースケジュール（提案書の導入ステップと整合） |
| 7. フェーズ別タスク・成果物 | wbs.yaml | タスク詳細、成果物一覧 |
| 8. 環境構成・技術要件 | requirements_master.md | 非機能要件から環境要件を抽出 |
| 9. ナレッジ・データ準備計画 | requirements_master.md | 対象ナレッジ、データ整備、登録フロー |
| 10. セキュリティ・ガバナンス計画 | requirements_master.md | アクセス制御、ログ・監査、AIリスク管理 |
| 11. コミュニケーション・変更管理 | project_charter.md | 会議体、報告ルール、変更管理プロセス |
| 12. リスクと対策 | risks.yaml, **proposal_draft.md** | リスク一覧と対策（提案書のリスクを詳細化） |

### データ抽出ルール

**proposal_draft.md から（上位成果物）:**
```
プロジェクトゴール → 「エグゼクティブサマリー」「提供価値」から目的・KPIを確認
スコープ → 「主要ユースケース」から対象範囲を確認
導入ステップ → 「導入ステップ」セクションからフェーズ構成の元ネタを取得
リスク → 「リスクと対策」から主要リスクを確認し詳細化
体制 → 「プロジェクト体制」から役割分担を確認し詳細化

※ 提案書と矛盾する内容がある場合は警告を出力
```

**wbs.yaml から:**
```yaml
# フェーズ構成の生成
フェーズ = tasks.phase の一意な値をリスト化
各フェーズのタスク = tasks[phase == target_phase]

# スケジュール生成
開始日 = min(tasks.due) または tasks[0].due - 見積期間
終了日 = max(tasks.due)
```

**project_charter.md から:**
```
体制 → 「体制」セクションをそのまま転記
スコープ → 「スコープ」「スコープ外」セクションを転記
```

### 品質チェックポイント（整合性・実現可能性重視）

計画書は「実行の基盤」が目的。提案書との整合性と実現可能性を最重視する。

| チェック項目 | 確認内容 | NG例 |
|-------------|---------|------|
| **提案書整合** | 提案書のスコープ・体制・スケジュールと矛盾がないか | 提案書にないタスクが含まれる |
| **5W1H明確** | 誰が・何を・いつまでに が全て明記されているか | 担当者未定のタスクが多い |
| **成果物定義** | 各フェーズの成果物が具体的に定義されているか | 「ドキュメント一式」のような曖昧な記述 |
| **依存関係** | タスク間の依存関係が明確か | 前提タスク未完了で開始するタスク |
| **リスク対応** | 提案書のリスクが全て対策付きで記載されているか | 提案書のリスクが欠落 |
| **バッファ** | 適切な予備期間が確保されているか | ギリギリのスケジュール |

**整合性チェック（自動）:**
```
提案書との差分チェック項目:
- スコープ: 提案書「主要ユースケース」⊆ 計画書「スコープ」
- 体制: 提案書「体制」の役割が計画書にも存在
- スケジュール: 提案書「導入ステップ」のフェーズ構成と一致
- リスク: 提案書「リスク」が計画書にも全て含まれる

不整合検出時: [整合性警告: 提案書との差分] を挿入
```

## 3. requirements_draft.md（要件定義書）

**テンプレート**: `templates/requirements.md`
**出力先**: `outputs/requirements_draft.md`
**上位成果物**: `outputs/proposal_draft.md`, `outputs/project_plan_draft.md`

### セクション別マッピング

| セクション | データソース | 抽出内容 |
|-----------|------------|---------|
| 1. 表紙 | project_charter.md | プロジェクト名、版数、日付 |
| 2. ドキュメント概要 | - | テンプレート固定（目的、対象読者、位置づけ） |
| 3. 背景・目的 | project_charter.md, **proposal_draft.md** | 目的、背景（提案書の課題認識・エグゼクティブサマリーと整合） |
| 4. 用語定義・略語一覧 | requirements_master.md, **proposal_draft.md** | 用語一覧（提案書で使用された用語を含む） |
| 5. 全体像（システム／業務アーキテクチャ） | project_charter.md, requirements_master.md, **proposal_draft.md**, **project_plan_draft.md** | システム概要、業務フロー（提案書のユースケース、計画書のスコープと整合） |
| 6. 業務要件 | requirements_master.md, **proposal_draft.md** | 業務シナリオ、ユースケース（提案書の主要ユースケースを詳細化） |
| 7. 機能要件 | requirements_master.md, **proposal_draft.md** | type=functionalの要件一覧（提案書のユースケースから導出） |
| 8. 非機能要件 | requirements_master.md, **project_plan_draft.md** | type=non-functionalの要件一覧（計画書の環境構成と整合） |
| 9. インターフェース要件 | requirements_master.md | 連携要件を抽出 |
| 10. データ要件 | requirements_master.md | データ関連要件を抽出 |
| 11. 制約条件・前提条件 | project_charter.md, decisions.yaml, **proposal_draft.md**, **project_plan_draft.md** | 制約、前提条件（提案書・計画書の前提を含む） |
| 12. 移行・展開要件 | requirements_master.md, wbs.yaml | 既存データ移行、段階的展開方針 |
| 13. テスト観点・受入条件 | requirements_master.md | テスト観点、受入条件 |
| 14. リスク・課題 | risks.yaml, issues.yaml, **proposal_draft.md**, **project_plan_draft.md** | オープンなリスク・課題（上位成果物のリスクを含む） |
| 15. 付録 | - | 参考資料一覧、変更履歴 |

### データ抽出ルール

**proposal_draft.md から（上位成果物）:**
```
背景・目的 → 「課題認識」「エグゼクティブサマリー」から背景を確認
ユースケース → 「主要ユースケース」から業務要件の元ネタを取得
用語 → 使用されている専門用語を抽出し用語定義に追加
リスク → 「リスクと対策」から要件関連リスクを確認

※ 提案書と矛盾する要件がある場合は警告を出力
```

**project_plan_draft.md から（上位成果物）:**
```
スコープ → 「スコープ定義」から要件の対象範囲を確認
環境構成 → 「環境構成」から非機能要件の制約を確認
フェーズ構成 → 「フェーズ構成」から各フェーズで必要な要件を確認
リスク → 「リスクと対策」から要件関連リスクを確認

※ 計画書と矛盾する要件がある場合は警告を出力
```

**requirements_master.md から:**
```
機能要件 → REQ-XXX where type == "functional"
  - ID、タイトル、概要、詳細、優先度を表形式で出力

非機能要件 → REQ-XXX where type == "non-functional"
  - カテゴリ別（性能、セキュリティ、可用性等）にグループ化
```

**open_questions.yaml から:**
```
status == "Open" の項目を「未決事項」として記載
関連する要件セクションに注記を追加
```

### 品質チェックポイント（網羅性・検証可能性重視）

要件定義書は「開発の基盤」が目的。IEEE 830基準を参考に網羅性と検証可能性を最重視する。

| チェック項目 | 確認内容 | NG例 |
|-------------|---------|------|
| **網羅性** | 提案書のユースケースが全て要件化されているか | 提案書のユースケースに対応する要件がない |
| **非曖昧性** | 解釈の余地がない明確な記述か | 「適切に」「迅速に」「必要に応じて」 |
| **検証可能性** | 各要件にテスト可能な合格基準があるか | 「使いやすい」「高速な」 |
| **追跡可能性** | 要件の出典（ヒアリング、決定）が明記されているか | 出典不明の要件 |
| **一貫性** | 要件間に矛盾がないか | 相反する要件が存在 |
| **優先度** | Must/Should/Could/Won't が定義されているか | 全て同じ優先度 |
| **TBD最小化** | 「TBD」「後日決定」が最小限か | TBDが10件以上 |

**曖昧語チェック（自動）:**
```
以下の曖昧語を検出し警告:
- 程度: 「適切に」「十分に」「迅速に」「高速に」「大量の」
- 条件: 「必要に応じて」「場合によっては」「できれば」
- 主観: 「使いやすい」「見やすい」「わかりやすい」

検出時: [曖昧性警告: 具体的な数値・条件を定義してください] を挿入
```

**網羅性チェック（自動）:**
```
提案書・計画書との網羅性チェック:
- 提案書「主要ユースケース」→ 対応する機能要件が存在するか
- 計画書「スコープ」→ スコープ内項目が要件化されているか
- 計画書「環境構成」→ 対応する非機能要件が存在するか

欠落検出時: [網羅性警告: 提案書のユースケースXXに対応する要件がありません] を挿入
```

**検証可能性チェック:**
```
各要件に以下が定義されているか確認:
- 合格基準（Acceptance Criteria）
- 測定方法（数値の場合）
- テスト方法の想定

未定義の場合: [検証可能性警告: 合格基準を定義してください] を挿入
```

## 共通ルール

### プレースホルダー形式
```markdown
[顧客名]           → project_charter.mdから取得
[プロジェクト名]    → project_charter.mdから取得
[YYYY-MM-DD]       → 現在日付または指定日付
[要入力: 項目名]   → データ未設定時の表示
[TBD]              → 後日決定事項
```

### データ不足時の動作
1. 必須項目が未設定: `[要入力: 項目名]`を挿入
2. 任意項目が未設定: セクションをスキップまたは空欄表示
3. 参照エラー: `[参照エラー: ファイル名]`を挿入し、警告出力

### 上位成果物が存在しない場合
1. **警告を出力**: 「上位成果物が存在しません: proposal_draft.md」
2. **project_stateのみで生成続行**: 上位成果物なしでも生成は可能
3. **メタデータに記録**: `parent_artifacts: none`と記載
4. **整合性チェックはスキップ**: 上位成果物との矛盾チェックは実施しない

**推奨**: 下位成果物を生成する前に、上位成果物を先に生成することを推奨。

### 上位成果物との整合性チェック
下位成果物生成時、以下の矛盾を検出した場合は警告を出力:
- スコープの不一致（対象範囲が異なる）
- スケジュールの不一致（フェーズ構成や期間が異なる）
- リスクの不一致（上位で挙げたリスクが下位に含まれていない）
- 体制の不一致（役割分担が異なる）

矛盾検出時は`[整合性警告: 詳細]`を該当箇所に挿入。

### 差分更新の判定
```
更新必要 =
  source_state.any(file.updated_at > draft.generated_at) OR
  parent_artifacts.any(file.updated_at > draft.generated_at) OR
  template.updated_at > draft.generated_at
```

### 手動編集の検出
```markdown
<!-- MANUAL START --> ... <!-- MANUAL END -->  → 保護
## セクション名 <!-- MANUAL -->               → セクション全体を保護
```
