## 1. 用語定義・略語一覧の確定（QST-033関連）

### 1.1 プロジェクト固有の用語
高松より、要件定義書で使用する用語の定義確認を依頼。佐伯部長、清水リーダーと合意した用語定義:

| 用語 | 定義 |
|------|------|
| **AIワークフロー** | AI Workforce基盤上で実行される業務フロー。複数のAIエージェントが連携して情報検索、分析、資料作成等を自動実行する仕組み |
| **ナレッジポータル** | 社内の情報資産（市況レポート、商品情報、FAQ等）を統合的に管理し、AIエージェントが参照可能な形式で保存するシステム |
| **統合検索** | 複数のデータソース（CRM、商品DB、市況レポートDB等）を横断的に検索し、関連情報を一覧表示する機能 |
| **要約エージェント** | 市況レポートや長文資料を要約し、重要ポイントを抽出するAIエージェント |
| **提案資料生成エージェント** | 顧客情報、商品情報、市況分析等を統合し、提案資料のドラフトを自動生成するAIエージェント |
| **RAG（Retrieval-Augmented Generation）** | 外部知識ベースから関連情報を検索し、その情報を基に回答を生成するAI技術。幻覚（hallucination）を抑制する効果がある |
| **幻覚（Hallucination）** | AIが事実に基づかない情報を生成してしまう現象。金融業界では致命的なリスクとなるため、RAGによる根拠提示で対策 |

### 1.2 業務用語
山口マネージャーより確認した業務用語:

| 用語 | 定義 |
|------|------|
| **リテール営業** | 個人投資家向けの営業活動。本プロジェクトの主な対象部門 |
| **富裕層（HNW）** | High Net Worth（純資産1億円以上）の顧客セグメント |
| **ポートフォリオ提案** | 顧客の資産状況、リスク許容度に基づき、複数の金融商品を組み合わせた資産運用提案 |
| **市況整理** | 市場動向、経済指標、業界トレンド等を分析し、顧客向けに説明可能な形にまとめる作業 |
| **NISA** | 少額投資非課税制度。2024年の制度改正により利用者が急増 |
| **CRM** | Customer Relationship Management。顧客情報管理システム（当社はSalesforceを使用） |

### 1.3 技術用語
田中（LayerX側アーキテクト）より説明、山根副部長と確認した技術用語:

| 用語 | 定義 |
|------|------|
| **Azure OpenAI Service** | Microsoft Azureが提供するOpenAI APIサービス。企業向けセキュリティとコンプライアンスを備えたGPTモデル利用基盤 |
| **Azure AI Search** | Azure上のベクトル検索・全文検索サービス。ナレッジポータルの検索エンジンとして使用 |
| **VPN（Virtual Private Network）** | 仮想プライベートネットワーク。セキュアな通信経路を確保 |
| **SSO（Single Sign-On）** | 一度の認証で複数システムにアクセス可能にする認証方式。Azure ADと連携 |
| **RBAC（Role-Based Access Control）** | ロールベースアクセス制御。ユーザーの役割に応じてアクセス権限を管理 |
| **Cosmos DB** | Azureのフルマネージドなマルチモデルデータベース。本プロジェクトではドキュメントDBとして使用 |

## 3. 業務ルール・判断ロジックの詳細（QST-035関連）

### 3.1 商品選定時の判断基準
佐伯部長、山口マネージャーより確認。AIエージェントが商品選定時に従うべきルール:

#### 3.1.1 顧客属性による商品フィルタリング
- **年齢**: 60歳以上の場合、リスクの高い商品（新興国株式ファンド等）は推奨しない
- **資産規模**: 運用資産1,000万円未満の場合、高額商品（一口100万円以上の債券等）は除外
- **リスク許容度**:
  - 「保守的」: 元本保証型、国内債券中心
  - 「バランス型」: 投資信託（バランス型、国内株式）中心
  - 「積極的」: 海外株式、新興国ファンド、個別株式も検討可
- **投資経験**: 初心者の場合、複雑な金融商品（仕組債、デリバティブ等）は除外

#### 3.1.2 コンプライアンス上の制約
- **適合性の原則**: 顧客の知識・経験・財産状況に適合しない商品は推奨しない
- **説明義務**: リスクが高い商品はリスク説明を必ず記載
- **禁止商品**: 社内で販売停止中の商品は除外
- **集中投資の回避**: 同一銘柄・同一セクターへの投資が総資産の30%を超えないよう推奨

#### 3.1.3 収益性の考慮
- **手数料水準**: 顧客にとって不利な高コスト商品は避ける
- **過去実績**: 直近1年・3年・5年の運用実績を考慮
- **分散投資**: 複数の資産クラス（株式、債券、REIT等）に分散することを推奨

### 3.2 提案資料のレビュー基準
清水リーダーより確認。上司レビュー時のチェック基準:

#### 3.2.1 内容の正確性
- [ ] 商品情報（利回り、手数料、リスク等級）が正確か
- [ ] 市況解釈が最新レポートに基づいているか
- [ ] 数値データ（グラフ、表）に誤りがないか

#### 3.2.2 コンプライアンス適合性
- [ ] 顧客の属性（年齢、資産、リスク許容度）に適合した商品提案か
- [ ] リスク説明が適切に記載されているか
- [ ] 誤解を招く表現（「絶対儲かる」等）がないか
- [ ] 免責事項が記載されているか

#### 3.2.3 提案品質
- [ ] 顧客ニーズに合致しているか
- [ ] 説明が分かりやすいか（専門用語の多用を避ける）
- [ ] 根拠（市況レポート、商品説明資料）が明示されているか
- [ ] 代替案が提示されているか

### 3.3 市況解釈のガイドライン
佐伯部長より確認。市況整理時に従うべきルール:

#### 3.3.1 情報ソースの信頼性
- **最優先**: 自社調査部発行の市況レポート
- **次点**: 公式統計（日銀、内閣府等）、主要メディア（日経、Bloomberg等）
- **参考程度**: SNS、個人ブログ等（エビデンスとしては不可）

#### 3.3.2 表現の中立性
- **禁止**: 断定的な表現（「〇〇は必ず上がる」「今が買い時」等）
- **推奨**: 条件付き表現（「〇〇の場合、上昇が期待される」「リスクも考慮が必要」等）
- **必須**: リスク・不確実性の明示

#### 3.3.3 時点の明示
- 市況レポートの発行日を明記
- 「〇月〇日時点の情報」と明示

## 4. 各機能の入力・出力項目、画面/API仕様の詳細（QST-036関連）

田中（LayerXアーキテクト）より提案、山根副部長と合意した仕様:

### 4.1 統合検索機能

#### 4.1.1 入力項目
| 項目名 | 型 | 必須 | バリデーション | 説明 |
|--------|-----|------|---------------|------|
| `query` | string | ○ | 1～500文字 | 検索キーワード（自然文も可） |
| `data_sources` | array[string] | - | enum: [CRM, 商品DB, 市況レポート, 規程DB, FAQ, 提案資料] | 検索対象（未指定時は全て） |
| `date_from` | date | - | YYYY-MM-DD形式 | 対象期間（開始日） |
| `date_to` | date | - | YYYY-MM-DD形式 | 対象期間（終了日） |
| `limit` | integer | - | 1～100、デフォルト20 | 最大取得件数 |

#### 4.1.2 出力項目
```json
{
  "results": [
    {
      "id": "string",               // 結果ID
      "source": "string",           // データソース名
      "title": "string",            // タイトル
      "snippet": "string",          // スニペット（抜粋）
      "url": "string",              // リンクURL（該当ドキュメントへの参照）
      "relevance_score": "float",   // 関連度スコア（0.0～1.0）
      "created_at": "datetime"      // ドキュメント作成日時
    }
  ],
  "total_count": "integer",         // 総件数
  "elapsed_time": "float"           // 検索時間（秒）
}
```

#### 4.1.3 API仕様
- **Endpoint**: `POST /api/v1/search`
- **認証**: Bearer Token（Azure AD発行）
- **レスポンスタイム目標**: 3秒以内（95パーセンタイル）

### 4.2 要約機能

#### 4.2.1 入力項目
| 項目名 | 型 | 必須 | バリデーション | 説明 |
|--------|-----|------|---------------|------|

| `summary_length` | string | - | enum: [short, medium, long]、デフォルトmedium | 要約の長さ（short: 200文字、medium: 500文字、long: 1000文字） |

## 5. AIエージェント/ワークフロー要件の詳細（QST-037関連）

田中（LayerXアーキテクト)より提案、佐伯部長と合意した仕様:

### 5.1 AIエージェントの役割定義

#### 5.1.1 統合検索エージェント
- **役割**: 複数データソースを横断的に検索し、関連情報を抽出
- **対話パターン**:
  - ユーザー: 「富裕層向けのNISA活用事例を探して」
  - エージェント: 「CRM、過去提案資料、FAQ DBから関連情報を検索しました。10件の事例が見つかりました」
- **使用技術**: Azure AI Search（ベクトル検索）、セマンティック検索
- **制約**: 同時検索は最大7データソース、タイムアウト5秒

#### 5.1.2 要約エージェント
- **役割**: 長文ドキュメント（市況レポート等）を要約
- **対話パターン**:
  - ユーザー: 「最新の市況レポートを要約して」
  - エージェント: 「2026年1月28日発行の市況レポートを要約しました。主要ポイントは以下の通りです: 1) 米国金利が上昇傾向、2) 日経平均は33,000円台で推移...」
- **使用技術**: Azure OpenAI Service（GPT-4）、RAG
- **制約**: 入力ドキュメントは最大10,000トークン（約30ページ相当）

#### 5.1.3 提案資料生成エージェント
- **役割**: 顧客情報、商品情報、市況分析を統合し、提案資料を生成
- **対話パターン**:
  - ユーザー: 「山田太郎様向けのNISA活用提案資料を作成して」
  - エージェント: 「山田太郎様の情報をCRMから取得しました。年齢55歳、リスク許容度バランス型、運用資産3,000万円。NISA枠を活用したバランス型ファンド中心のポートフォリオ提案を作成しました」
- **使用技術**: Azure OpenAI Service（GPT-4）、PowerPoint生成API
- **制約**: 生成時間は最大30秒、テンプレートは最大10スライド

### 5.2 ワークフローステップ構成

#### 5.2.1 ポートフォリオ提案ワークフロー
```
[入力]
├─ ユーザー: 顧客ID、提案種別
↓
[ステップ1: 情報収集]
├─ 統合検索エージェント: CRMから顧客情報取得
├─ 統合検索エージェント: 商品DBから適合商品検索
├─ 要約エージェント: 最新市況レポート要約
↓
[ステップ2: 分析]
├─ 分析エージェント: 顧客属性分析（年齢、資産、リスク許容度）
├─ 分析エージェント: 商品適合性判定（コンプライアンスチェック含む）
├─ 分析エージェント: ポートフォリオ最適化（リスク分散）
↓
[ステップ3: 生成]
├─ 提案資料生成エージェント: PowerPoint資料生成
├─ 提案資料生成エージェント: 根拠資料のリンク挿入
↓
[ステップ4: 検証]
├─ 検証エージェント: 数値データの正確性チェック
├─ 検証エージェント: コンプライアンスルール適合確認
├─ 検証エージェント: 禁止表現チェック
↓
[出力]
├─ 提案資料（PowerPoint）
├─ 根拠資料一覧
└─ チェックリスト
```

#### 5.2.2 市況整理ワークフロー
```
[入力]
├─ ユーザー: 期間指定（例: 直近1週間）
↓
[ステップ1: 情報収集]
├─ 統合検索エージェント: 市況レポートDB検索
├─ 統合検索エージェント: 外部ニュース取得（Bloomberg、日経等）
↓
[ステップ2: 分析]
├─ 要約エージェント: 各レポートの要約
├─ 分析エージェント: トレンド分析（上昇/下降/横ばい）
├─ 分析エージェント: 重要イベント抽出
↓
[ステップ3: 生成]
├─ 提案資料生成エージェント: 市況サマリー生成
└─ 提案資料生成エージェント: 顧客向け説明文生成
↓
[出力]
├─ 市況サマリー（PDF/PowerPoint）
└─ 参照レポート一覧
```

### 5.3 再実行・再生成・フィードバック反映

#### 5.3.1 再実行要件
山口マネージャーより要望:
- **ユースケース**: AI生成結果が意図と異なる場合、パラメータを調整して再実行
- **実装**:
  - 「再実行」ボタンを配置
  - 前回の入力パラメータを保持し、修正可能にする
  - 実行履歴（最大10件）を保存
- **制約**: 同一ワークフローの再実行は最大5回まで（無限ループ防止）

#### 5.3.2 再生成要件
清水リーダーより要望:
- **ユースケース**: 提案資料の一部（特定スライド、説明文等）のみ再生成
- **実装**:
  - スライド単位での再生成ボタン
  - 説明文の「書き直し」ボタン
  - 別の商品候補を提案する「代替案生成」ボタン
- **制約**: 再生成は該当箇所のみ（全体は再実行を使用）

#### 5.3.3 フィードバック反映
佐伯部長より要望:
- **ユースケース**: ユーザーからのフィードバックを蓄積し、AI精度を向上
- **実装**:
  - 各生成結果に「良い/悪い」評価ボタン
  - 「なぜ悪いか」のフィードバックコメント入力欄（任意）
  - フィードバックはログとして蓄積、定期的にモデル改善に活用
- **制約**: フィードバックは匿名化してLayerX側で分析（個別顧客情報は除外）

## 10. 拡張性・保守性要件（ユースケース追加時の影響等）（QST-042関連）

田中（LayerXアーキテクト）より提案:

### 10.1 ユースケース追加時の影響範囲

#### 10.1.1 設計方針
- **プラグインアーキテクチャ**: 新規ユースケースは既存機能に影響を与えずに追加可能
- **ワークフローテンプレート**: 新規ワークフローはテンプレート形式で定義（コード変更最小化）
- **設定ファイル駆動**: ワークフローの構成は設定ファイル（YAML/JSON）で管理

#### 10.1.2 追加時の作業範囲
| 作業項目 | 見積もり工数 | 影響範囲 |
|---------|------------|---------|
| **ワークフロー定義作成** | 2～5日 | 設定ファイルのみ |
| **UI画面追加** | 3～7日 | フロントエンド（新規画面のみ） |
| **テスト** | 3～5日 | 新規機能のみ（既存機能への回帰テストは最小限） |
| **ドキュメント更新** | 1～2日 | ユーザーマニュアル |

**合計: 約2～3週間**（複雑度により変動）

### 10.2 ワークフロー変更時の設計ポリシー

#### 10.2.1 変更容易性の確保
- **ステップ単位の独立性**: 各ワークフローステップ（検索、分析、生成、検証）は独立したモジュールとして実装
- **依存関係の明示**: ステップ間の依存関係は設定ファイルで明示的に定義
- **バージョン管理**: ワークフロー定義はバージョン管理し、ロールバック可能

#### 10.2.2 変更時の影響最小化
- **既存ワークフローへの影響なし**: 新規ワークフローや変更は既存ワークフローに影響しない
- **A/Bテスト可能**: 新旧ワークフローを並行稼働し、効果検証可能

### 10.3 新規データソース追加時の対応方針

#### 10.3.1 追加時の作業範囲
| 作業項目 | 見積もり工数 | 影響範囲 |
|---------|------------|---------|
| **データソースコネクタ開発** | 5～10日 | 新規コネクタのみ |
| **データ変換・マッピング定義** | 2～5日 | 新規データソースのみ |
| **インデックス作成** | 1～3日 | Azure AI Search設定 |
| **テスト** | 3～5日 | 新規データソースのみ |

**合計: 約2～4週間**（データソースの複雑度により変動）

#### 10.3.2 設計方針
- **抽象化レイヤー**: データソースアクセスは抽象化レイヤー経由で統一
- **コネクタパターン**: 各データソースはコネクタパターンで実装（REST API、DB接続、ファイル取り込み等）
- **スキーママッピング**: データソースごとのスキーマ差異はマッピング定義で吸収

### 10.4 将来の機能拡張に向けた設計方針

#### 10.4.1 想定される将来拡張
佐伯部長より以下の将来拡張を想定:

1. **他部門への展開** (Phase 3以降)
   - 法人営業部門への拡張
   - リスク管理部門への拡張
   - 影響: ユーザー数増加、データソース追加、ワークフロー追加

2. **多言語対応** (将来検討)
   - 英語、中国語対応
   - 影響: UI多言語化、AIモデルの多言語対応

3. **モバイルアプリ** (将来検討)
   - スマートフォンアプリ提供
   - 影響: モバイルUI開発、APIの拡張

#### 10.4.2 拡張性を確保する設計
- **マルチテナント対応**: 部門別データ分離、権限管理
- **APIファースト設計**: すべての機能はAPI経由でアクセス可能（モバイル対応容易）
- **国際化対応**: UI文言は外部ファイルで管理（多言語対応容易）

## 13. 受入条件（システム受入の条件）（QST-045関連）

佐伯部長、山根副部長と合意した受入条件:

### 13.1 機能面の受入条件

#### 13.1.1 必須機能（Phase 1）
以下の機能が仕様通りに動作すること:

- [ ] **統合検索機能**
  - CRM、商品DB、市況レポートDB、社内規程DB、FAQ DB、過去提案資料の横断検索が可能
  - 検索結果が関連度順に表示される
  - 検索レスポンス時間が3秒以内（95パーセンタイル）

- [ ] **要約機能**
  - 市況レポート、ドキュメントの要約が生成できる
  - 要約が元ドキュメントの内容を正確に反映している
  - 重要ポイントが抽出されている

- [ ] **提案資料生成機能（ポートフォリオ提案）**
  - 顧客情報を基にポートフォリオ提案資料が生成できる
  - 商品選定が顧客属性（年齢、リスク許容度等）に適合している
  - 提案資料がPowerPoint形式でダウンロード可能
  - 根拠となる情報源が明示されている

- [ ] **提案資料生成機能（NISA活用支援）**
  - NISA制度説明、商品説明を含む資料が生成できる
  - NISA対象商品が正確に選定されている

- [ ] **提案資料生成機能（市況アップデート）**
  - 最新市況レポートを基に市況サマリーが生成できる
  - 顧客向け説明文が生成できる

- [ ] **再生成機能**
  - 提案資料の再生成が可能
  - 商品変更、説明文変更が可能

- [ ] **履歴管理機能**
  - 検索履歴、生成した提案資料の履歴が閲覧可能
  - 自分が作成した提案資料のみ閲覧可能（営業担当者）

- [ ] **レビュー機能**
  - 提案資料にレビューコメントを追加可能（上司）

### 13.2 非機能面の受入条件

- [ ] **障害通知**: 障害発生時に30分以内に通知

#### 13.2.3 セキュリティ要件
以下のセキュリティ要件を満たすこと:

- [ ] **認証**: Azure AD SSOでログイン可能
- [ ] **認可**: ロールベースアクセス制御（RBAC）が機能している
- [ ] **暗号化**: データ保存時・通信時ともに暗号化されている
